System integration

Daily briefing and alerting platform

Scheduled jobs read mail, calendars, reminders, finances, and weather from a dozen sources, assemble one briefing for a phone dashboard and a bedside display, and page me when a job or service breaks. It has run accurately for months without my intervention.

The problem

The information I check every day lives in a dozen places that were never designed to talk to each other: two Gmail accounts, Google Calendar, an Outlook calendar, Apple Reminders, a personal-finance app with no public API, a weather service, a fantasy baseball league's export tracker, and a few more. I didn't want to keep having to check each of these platforms several times a day.

The harder problem was not reading any one source. It was making the whole thing dependable enough to run for months unattended, and safe enough to touch mail and finances without ever changing them.

What it does

Every two hours during the day, a job on my Mac assembles a briefing: weather and air quality, the day's calendar from both sources, a cash position, open reminders, a triaged summary of new mail, and a few personal trackers. It renders the result and pushes it to a password-gated dashboard on a small server, installed on my phone as a web app. The same server feeds the bedside display, so calendar and weather reach an OLED screen on the nightstand.

Where the data comes from

  • Gmail, through an OAuth client I wrote as a local CLI. It fetches headers only and has no code path that labels, archives, trashes, or sends.
  • Google Calendar through the official API on a read-only scope, and an Outlook calendar through a published sheet export.
  • Apple Reminders through a small Swift helper compiled against EventKit, because there is no API and AppleScript cannot see enough.
  • A cash position from a personal-finance app with no public API, through a community client wrapped in a read-only script.
  • Weather and air quality, a fantasy baseball league's export tracker, a flight-data API's usage meter, and, in a sibling job, last.fm plays and a reading list.

Where it goes

  • A hosted dashboard, installed as a web app on my phone. The Mac uploads rendered HTML through a token-authenticated, upload-only endpoint.
  • The bedside OLED display, which reads calendar, weather, subway arrivals, and lights from the same server.
  • Google Calendar, where a weekly job writes upcoming album and book releases as all-day events.
  • Apple Reminders, through a second compiled CLI that can set repeat rules, which AppleScript cannot.
  • macOS notifications, through one shared notification path that every scheduled job calls.
  • Email, sent from me to me by the monitoring job when a deployed service raises a new alert signal.
  • Drafted email that is never sent: a twice-weekly job for my congregation reads the Sunday sign-up sheet, flags unfilled roles two Sundays out, and writes the reminder for me to review.

Architecture

Sources → shared read-only plumbing → ten scheduled jobs on the Mac and one service on the server → seven surfaces. A monitoring layer probes the server, the tokens, and the jobs themselves, and pages back through the same notification path.

Hardening that mattered

Most of the engineering went into the parts that fail quietly.

Auth that heals itself

  • The finance app's saved session dies on its own schedule. The script re-authenticates with a one-time code on a fresh client when the failure is auth-shaped. Network errors propagate instead of triggering a login.
  • The community client shipped with certificate verification off. I wrapped it to force verification on before trusting it with a login.
  • Google's restricted mail scope expires its token roughly weekly on an unverified app. An hourly job checks token freshness for both accounts and re-nags until I re-authorize.

Failure that announces itself

  • A server-side timer probes each deployed service every five minutes, and a Mac-side probe checks the same endpoints from outside. A check has to stay red for two consecutive runs before anyone gets paged.
  • A morning job pages for any scheduled job that missed its run overnight.
  • The notification path never waits on the user. The tool it replaced blocked on an undismissed alert and leaked memory until two of them took the Mac down.

Writes that cannot surprise

  • The dashboard gate compares tokens in constant time, and the ingest endpoint accepts uploads only. Sources that rate-limit are cached once a day.
  • Every project in the workspace is tiered by blast radius. Anything with an irreversible external effect earns guard tests of its dry-run default and refusal paths, a public service earns a smoke test, and local one-shots earn none. The briefing pipeline carries 380 tests.

The feedback loop

Mail triage is the one place a language model runs in the pipeline, a single batched call on a small model each refresh. Buttons on the dashboard record a verdict on each suggestion into an append-only ledger, and a free-text note records anything else. "Not this kind" verdicts become sender and topic suppressions that expire after ninety days. A weekly job sweeps the notes into a review, and I promote the durable ones into the standing preferences the classifier honors.

How I built it with AI

This is integration work across systems I did not know, built with coding agents: EventKit and Swift for the Reminders helper, launchd for scheduling, systemd and nginx on the server, an undocumented GraphQL schema for the finance app. What I brought was the operations discipline: decide what counts as a source of truth, decide which paths may write, test the guards rather than the views, and inventory what is deployed. The most useful decision was writing four small Google CLIs instead of using the agent-side connectors, which were convenient for a single read and wrong for scheduled bulk work.
