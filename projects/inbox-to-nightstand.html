System integration

Inbox to nightstand

A personal operations stack: a dozen sources read through official APIs, unofficial ones, and CLIs I had to build, delivered to seven surfaces, and hardened until it runs unattended.

The problem

The information I check every day lives in a dozen places that were never designed to talk to each other: two Gmail accounts, Google Calendar, an Outlook calendar exported by an employer, Apple Reminders, a personal-finance app with no public API, a weather service, a baseball league's export tracker, and a few more. Checking each one by hand is a tax paid several times a day, and the phone that pays it is the same phone I wanted out of the bedroom.

The harder problem was not reading any one source. It was making the whole thing dependable enough that a scheduled job could run for months without me, and safe enough that it could touch mail and finances without ever changing them.

What it does

Every two hours during the day, a job on my Mac assembles a briefing: weather and air quality, the day's calendar from both sources, a cash position, open reminders, a triaged summary of new mail, and a few personal trackers. It renders the result and pushes it to a password-gated dashboard hosted on a small server, installed on my phone as a web app. The same server feeds the bedside display, so calendar and weather reach an OLED screen on the nightstand without a phone in the room.

Where the data comes from

  • Gmail, through an OAuth client I wrote as a local CLI. It fetches headers only and has no code path that labels, archives, trashes, or sends.
  • Google Calendar through the official API on a read-only scope, plus an employer's Outlook calendar as a published sheet export.
  • Apple Reminders through a small Swift helper compiled against EventKit, because there is no API and AppleScript cannot see enough. Read every run, never written.
  • A cash position from a personal-finance app that has no public API, through a community client wrapped in a read-only script.
  • Weather and air quality, a baseball league's export tracker, a flight-data API's usage meter, and, in a sibling job, last.fm plays and a reading list.

Where it goes

  • A hosted dashboard, installed as a web app on my phone. The Mac uploads rendered HTML through a token-authenticated, upload-only endpoint. The server never reaches back.
  • The bedside OLED display, which reads calendar, weather, subway arrivals, and lights from the same server.
  • Google Calendar, where a weekly job writes upcoming album and book releases as all-day events. Dry run by default, an explicit flag to write, idempotent event IDs so a re-run never duplicates.
  • Apple Reminders, through a second compiled CLI that can set repeat rules, which AppleScript's Reminders dictionary cannot.
  • macOS notifications, through one shared notification path that every scheduled job calls, with a level-to-channel policy that decides what merely informs and what pages.
  • Email, sent from me to me by the monitoring job when a deployed service raises a new alert signal, remembered in a state file so the same signal never pages twice.
  • Drafted email that is never sent: a twice-weekly job for my congregation reads the Sunday sign-up sheet, flags unfilled roles two Sundays out, writes the reminder, and offers to open it. Sending is a human act.

An earlier version was triggered from Apple Shortcuts and delivered by email. Both were retired once the scheduled jobs and the dashboard were dependable. The stack now runs on ten scheduled jobs on the Mac and one isolated service on the server, each recorded in a deployment inventory that is the single source of truth for what is live.

Architecture

Sources → shared read-only plumbing → scheduled jobs on the Mac and one service on the server → seven surfaces. A monitoring layer probes the server, the tokens, and the jobs themselves, and pages back through the same notification path.

Hardening that mattered

Most of the engineering went into the parts that fail quietly.

Auth that heals itself

  • The finance app's saved session dies on its own schedule. The script now re-authenticates with a time-based one-time code on a fresh client when, and only when, the failure is auth-shaped. Network errors propagate instead of triggering a login. The first version re-authenticated the same client and failed, because it carried stale state.
  • The community client's transport shipped with certificate verification off. I wrapped it to force verification on before trusting it with a login.
  • Google's restricted mail scope expires its refresh token roughly weekly on an unverified app. Rather than fight it, an hourly job checks token freshness for both accounts and posts a notification that re-nags until I click it, which re-runs the authorization.

Failure that announces itself

  • A server-side timer probes each deployed service every five minutes. A Mac-side probe checks the same endpoints from outside. A check has to stay red for two consecutive runs before anyone gets paged.
  • A morning job pages a failure for any scheduled job that missed its run overnight, so a silently unloaded job is caught the same day.
  • The notification path never waits on the user. The tool it replaced blocked on an undismissed alert and leaked memory without bound while waiting, and two of them took the Mac down. Now a notification is fire-and-forget, and an email that cannot send lands in a log instead of a retry loop.

Writes that cannot surprise

  • The dashboard gate compares tokens in constant time, and the ingest endpoint accepts uploads only. Each source that can rate-limit is cached once a day, and the one flaky upstream API retries with backoff.
  • Every project in the workspace is tiered by blast radius. Anything with an irreversible external effect, mail, money, calendar writes, earns guard tests of its dry-run default and refusal paths. A public service earns a smoke test that it boots. Local one-shots earn none. The briefing pipeline alone carries 380 tests, including one that fails if a dry run ever touches its state database.

The feedback loop

Mail triage is the one place a language model runs in the pipeline, a single batched call on a small model each refresh. Its judgment improves through a loop that is deliberately half-automatic. Buttons on the dashboard record a verdict on each suggestion, and a free-text note records anything else, into an append-only ledger. Verdicts of "not this kind" become sender and topic suppressions that expire after ninety days, with no model involved. A weekly job sweeps the notes into a review. Promotion into the standing preferences the classifier honors is done by hand, on purpose, so the rules the model follows are rules I wrote.

How I built it with AI

This is integration work across systems I did not know, built with coding agents: EventKit and Swift for the Reminders helper, launchd for scheduling, systemd and nginx on the server, an undocumented GraphQL schema for the finance app. What I brought was the operations discipline: decide what counts as a source of truth, decide which paths may write, test the guards rather than the views, and inventory what is deployed so nothing runs that no one remembers.

The most useful lesson came from choosing not to use the tooling that was easiest to reach. The agent-side connectors for Google services were convenient for a single read and wrong for scheduled bulk work, and the standard admin tooling cannot reach consumer accounts at all. Writing four small CLIs took an afternoon and removed a class of failures for good.

What I learned

Unattended is a different standard from working. A pipeline that runs when you watch it is a demo. One that runs at 7am for months, tells you when it cannot, and never sends an email you did not write is infrastructure. The difference is almost entirely in the failure paths, and none of it shows on the dashboard.
